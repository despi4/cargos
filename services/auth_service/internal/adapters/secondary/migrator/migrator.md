## Migrator(Как работает embed.FS и iofs)

Этот код нужен для того, чтобы читать файлы миграций прямо из оперативной памяти  
 скомпилированного бинарника, а не с жесткого диска.

Давай разберем это просто и наглядно.  
 ──────

### В чём проблема обычного подхода?

Обычно библиотеке миграций говорят:

    m, err := migrate.New("file://services/auth_service/migrations", dsn)

Здесь драйвер file:// идет на реальный жесткий диск операционной системы и ищет папку с файлами  
 .sql.

Почему это создает проблемы:

1. В Docker: при сборке контейнера нужно помнить скопировать папку migrations внутрь образа (COPY
   migrations ./migrations). Забудешь — сервис при старте упадет с ошибкой «папка не найдена».
2. Пути: если ты запускаешь сервис из корня проекта — путь один, если зашел в cmd/api и нажал go
   run main.go — путь другой. Приходится постоянно подгонять относительные пути.  
   ──────

### Как это решает iofs и embed.FS в Go

Начиная с Go 1.16, появилась фича embed: компилятор Go может взять любые текстовые файлы (наши  
 .sql) и «вшить» их внутрь скомпилированного исполняемого файла (бинарника).

Код выглядит так:

    import "embed"

    //go:embed migrations/*.sql
    var migrationFS embed.FS

Теперь все SQL-файлы сидят внутри переменной migrationFS в бинарнике в виде байтов в памяти. На  
 диске файлы больше вообще не нужны!  
 ──────

### А зачем тогда iofs.New(fs, dir)?

Библиотека golang-migrate очень старая и исторически умеет работать с источниками через  
 специальные драйверы источников (source drivers):

• file:// — читает с локального диска;  
 • github:// — качает файлы миграций с гитхаба;  
 • s3:// — качает из хранилища Amazon S3;  
 • iofs — читает из виртуальной файловой системы Go (io/fs.FS или embed.FS).

Строка:

    d, err := iofs.New(fs, dir)

делает ровно одну вещь:

│ Создает адаптер-переходник (d), который объясняет golang-migrate:  
 │ «Не ищи файлы на диске! Читай их вот из этой виртуальной структуры fs из папки dir, которая уже
│ вшита в память программы».

После этого мигратор запускается так:

    // Передаем созданный адаптер "iofs" вместо пути "file://..."
    m, err := migrate.NewWithSourceInstance("iofs", d, dsn)

### Итог: какая от этого польза?

• Получается один единственный бинарник, в котором внутри уже есть всё: код сервиса, веб-сервер и файлы миграций.
• Больше никаких проблем с file not found и путями в Docker или локально. Вы можете перенести  
 бинарник на чистый сервер без исходного кода, запустить его — и он сам создаст и обновит все  
 таблицы в базе данных.
